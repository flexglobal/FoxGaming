# Mono Messenger Relay v3

Небольшой временный сервер доставки сообщений для Mono Browser.

## Что изменилось

Вместо WebRTC SDP `offer/answer` используется `/api/messages`:

- `POST /api/messages {action:"send",from,to,payload,id}` — принять сообщение в очередь (HTTP 202).
- `GET /api/messages?id=MONO-...&action=poll` — получить сообщения без удаления.
- `POST /api/messages {action:"ack",id,ids}` — подтвердить получение и удалить эти сообщения.
- `POST /api/messages {action:"ping",id}` — отметка активности на 35 секунд.
- `GET /api/messages?id=MONO-...&action=presence` — узнать, находится ли собеседник в сети.
- `GET /api/health` — проверка Redis и версии сервера.

Для авторизованных запросов используется заголовок `X-Mono-Token`: постоянный секрет
установки, производный от локальной идентичности Mono. В Redis хранится хеш токена,
а не сам токен. **Никогда не отправляй токен в публичных сообщениях и репозитории.**

## Публикация

1. Распакуй **содержимое этого архива в корень репозитория** уже существующего сервера.
   Проверь наличие файла `api/messages.js` именно в корне проекта, а не внутри ещё одной папки.
2. В настройках проекта укажи переменные среды:
   - `UPSTASH_REDIS_REST_URL` — HTTPS REST URL именно нужной базы Upstash.
   - `UPSTASH_REDIS_REST_TOKEN` — REST Token этой же базы.
3. Запусти новый деплой Production.
4. Открой `https://fox-gaming563gc.vercel.app/api/health`.
   Рабочий ответ содержит:
   ```json
   {"ok":true,"relayReady":true,"redis":"connected","version":"3.0.0"}
   ```
5. Обнови **оба клиента Mono** из архива клиента, который идёт вместе с этим сервером.

Старый WebRTC-обработчик `/api/signal` намеренно возвращает `410` — он больше не нужен.

## Хранение данных и ограничения

- Очереди в Redis **временные**: сообщение удаляется после подтверждения получателя
  или через 300 секунд. Постоянная история сообщений не создаётся.
- Это не полностью stateless-протокол: без короткой временной очереди нельзя доставить
  сообщение пользователю, который не опрашивает сервер в ту же миллисекунду.
- Публичные данные профиля проходят через очередь в момент отправки.
- Секрет подтверждения установки хранится как SHA-256 в Redis со сроком жизни 24 часа,
  пока установка активна он продлевается.
- **E2EE пока нет.** HTTPS защищает соединение по сети, но сервер может видеть
  сообщения в момент временного хранения. Для секретов потребуется отдельное E2EE.
- Один получатель может временно иметь до 48 невзятых кусков файла в очереди.
  Передающая сторона ждёт освобождения места. Передача больших файлов (100/150 МБ)
  расходует много HTTP-запросов и не гарантируется на бесплатных квотах хостинга.
- При отключении адресата недоставленные сообщения удалятся по TTL.

## Проверки

Из исходной папки разработки можно выполнить `node tests/relay-test.cjs`.
Клиент и сервер также протестированы через две изолированные страницы Chromium
на отправку текстов, профиля, изображения и файла из нескольких кусочков.
**Реальный деплой на аккаунте пользователя не проверялся.**

## Сообщение Node.js `DEP0169`

Предупреждение о `url.parse()` связано с устаревшим вызовом в среде выполнения
или зависимостях. Сама новая серверная логика использует современный `URL`.
Предупреждение **не объясняет** ошибку WebRTC `wrong state: stable`.

## v3.1: каналы, медали, активность в играх, постоянный владелец ID

Новые и изменённые эндпоинты (все требуют `X-Mono-Token`):

- `POST /api/channels` — настоящие каналы: `create, mine, get, search, subscribe, unsubscribe, post, delete-post, like, comments, comment, delete-comment, update, add-admin, remove-admin, delete`. Права (владелец / администратор / подписчик), лимиты и антиспам проверяются на сервере.
- `GET/POST /api/profile` — в ответе `verifiedBadges` (медали считает сервер, клиентским заявкам верить нельзя) и `gameActivity`.
- `POST /api/game-activity` — `{monoId, activity|null}`; игра проверяется по каталогу `lib/game-catalog.js`, не чаще 1 раза в 9 минут, TTL 12 минут.
- `POST /api/admin` — выдача ролей (`beta`, `staff`, `bug_hunter`), VIP (`set-vip`), дата регистрации (`set-created`). Работает только если задана переменная среды `MONO_ADMIN_TOKEN` (не короче 24 символов); заголовок `X-Mono-Admin`.
- `/api/chess` и `/api/messages` — владелец Mono ID закрепляется навсегда (`mono:acct:v1:owner:<id>`). Раньше через 24 часа сессия истекала и честный игрок получал «Проверка Mono ID не пройдена», а чужой токен мог занять ID.

Переменные среды: `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` и (по желанию) `MONO_ADMIN_TOKEN`.

В проекте 12 серверных функций (после `api/wallet.js`) — это ровно лимит бесплатного плана Vercel (12). Новые функции добавлять без объединения не получится.

Дата регистрации для медали «Год с Mono» у старых пользователей считается с первого запроса после обновления. Исправить вручную: `POST /api/admin {action:"set-created", id:"MONO-…", at:1738281600000}` (`at` — время в миллисекундах).

### Тесты

`npm test` поднимает настоящий `redis-server` на порту 6390 (должен быть установлен) и прогоняет 20 сценариев: захват чужого ID, медали, активность, права в каналах, ранговые шахматы (ELO, ничья, таймаут, дружеская партия, реванш, лидерборд, гонки).


## v3.2: кошелёк, подарки, экономия запросов

### `POST /api/wallet` — серебряные монеты и подарки
Требует `X-Mono-Token`. Все цены, награды, срок 3 дня и 70 % возврата определяет сервер (`lib/gifts.js`); числа от клиента игнорируются.

- `state` → `{balance, claimed[], gifts[], gone[], ledger[], now, sellHoldMs, sellPercent}`
- `claim-level {level, key}` — серебро за уровень (раз на аккаунт). Награды: 1→100, 2→200, 4→250, 6→250, 8→250, 10→500, 12→250, 13→350, 14→500.
- `send-gift {to, gift, key}` — списывает цену, подарок появляется в инвентаре получателя.
- `sell-gift {uid, key}` — не раньше чем через 3 дня после отправки; владелец получает 70 % (округление вниз); подарок удаляется из инвентаря и помечается «проданным» у отправителя и получателя на 30 дней.

Защита от дюпа: каждая операция — один атомарный Lua-скрипт в Redis (проверка + списание + выдача); обязательный одноразовый `key` (повтор запроса возвращает прежний результат и ничего не меняет, 24 ч); подарок — запись с серверным `uid` у одного владельца; лимиты — 60 отправок/час на аккаунт, 60 наград/сутки на IP, 500 подарков в инвентаре, аккаунт младше 20 секунд награды не получает. Баланс не может стать отрицательным.

**Честное ограничение:** уровень игрока считается на клиенте (XP от достижений), сервер не может проверить, что игрок действительно дошёл до уровня. Он гарантирует только «каждая награда один раз на аккаунт» и общий потолок 2 650 серебра на Mono ID. Чтобы убрать и эту лазейку, XP/достижения надо начислять на сервере.

### Экономия запросов (лимит 500 000/мес)
- `GET /api/messages?action=poll&hb=<сек>&peers=<id,id>` — один запрос заменяет прежние `ping` + `poll` + `presence-batch` (heartbeat, сообщения и статусы друзей приходят вместе). Старые `ping`/`presence-batch` остались для совместимости.
- TTL конвертов в relay увеличен с 300 до 600 секунд (клиент теперь опрашивает реже, но не реже чем раз в 150 с).
- Клиент опрашивает адаптивно: открытый мессенджер 10–30 с, закрытая панель 60–150 с, свёрнутое окно/бездействие 90–150 с; пустые ответы постепенно замедляют опрос. Каналы: 30 с только пока канал открыт и окно видно; список каналов — раз в 10 минут. Шахматы: 1,5 с пока ходит соперник (до 4 с при долгой паузе), 6 с на своём ходу.
- Оценка (грубая, не измерена на живых людях): активный пользователь ≈ 1 000–2 000 запросов в сутки, фоновый (программа открыта, мессенджер не используется) ≈ 250–700. Бесплатного лимита (≈16 000 запросов в сутки) хватит примерно на **15–35 ежедневных пользователей**. Для большего числа людей нужен не опрос, а push (WebSocket/SSE на отдельном сервисе, например Cloudflare Workers/Durable Objects или Ably) либо платный план.

## v3.3: админ-панель, баны, баг-репорты, объявления

**Новых функций-файлов Vercel нет** (на Hobby лимит 12 — сейчас ровно 12): панель живёт в `api/admin.js`, страница — в `lib/admin-page.js`, баг-репорты принимает `api/news.js`.

### Что нужно задать в Vercel (Settings → Environment Variables), затем сделать Redeploy
| Переменная | Что это |
|---|---|
| `MONO_ADMIN_PATH` | секретная часть ссылки, 16–80 символов `A-Z a-z 0-9 _ -` (например случайная строка из менеджера паролей). Панель открывается по `https://<домен>/a/<MONO_ADMIN_PATH>`; любой другой адрес → 404 |
| `MONO_ADMIN1_PASS` | пароль админа 1 (≥ 12 символов) |
| `MONO_ADMIN2_PASS` | пароль админа 2 (≥ 12 символов, не такой же, как у первого) |
| `MONO_ADMIN1_NAME`, `MONO_ADMIN2_NAME` | необязательно: имена в журнале |

Ни пароли, ни ссылка в репозитории не хранятся. Одновременно может быть **2 сессии** (по одной на админа; новый вход того же админа вытесняет старый вход). Сессия — случайный токен 256 бит (в Redis хранится только его SHA-256), простой 2 часа, максимум 12 часов.

### Возможности панели
Пользователи (поиск, сортировка, карточка) · бан/разбан (навсегда или на N дней, причина видна пользователю) · начислить/забрать серебро (баланс не уходит в минус, запись в историю кошелька) · выдать/забрать любую из 12 медалей · редактор ELO, сброс ELO у ВСЕХ (до 200, с копией на 30 дней и возвратом) · аналитика · объявления (появляются в колокольчике уведомлений у всех; клиенты проверяют раз в ~55 минут) · баг-репорты (бот «Mono», команда `/bug текст`: 3 в сутки с аккаунта, до 1000 слов) · консоль (журнал действий админов).

### Защита ввода пароля
Поле пароля — **только данные**. Пароль принимается как строка ≤ 200 символов, хэшируется (scrypt) и сравнивается по хэшу за постоянное время с обоими паролями; он не разбирается как JSON/команда, не попадает в Redis, логи и журнал. Действие определяется только полем `op` из белого списка (`Map`), поэтому «ввести команду вместо пароля» невозможно: любая строка/объект/массив вместо пароля = «неверный пароль». Подбор: 5 неверных попыток с адреса → блок на 15 минут, 40 неверных на весь сервис → вход закрыт на 15 минут. Правка ELO, сброс и возврат рейтинга требуют **повторного ввода пароля** того же админа (3 ошибки подряд закрывают сессию). Проверяется тестами `tests/admin-test.cjs` (≈ 60 враждебных значений в поле пароля).

### Баны
Бан не добавляет запросов: значение ключа владельца аккаунта меняется на `banned:<прежний хэш>`, обычная проверка токена перестаёт совпадать (мессенджер, чат, шахматы, кошелёк, профиль, каналы закрываются, активные сессии сбрасываются). Причину видит только прежний владелец. Временный бан снимается сам. Ограничение: бан привязан к Mono ID — новая установка получит новый ID.
